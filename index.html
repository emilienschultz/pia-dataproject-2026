General workflow - today, first step

The unholy trinity

Every data project combines three things

  • Data
  • Code: scripts, notebooks, treatments
  • Compute: the machine running the code

Each has its own tools and best practices. Most problems come from mixing them.

And now, also AI

Is it a fourth dimension?

  • Models, workflows, tooling…

What does it change?

A lot of practices, but not the general philosophy or architecture we see today. And it makes reproducibility harder (which model? which version? which prompt?).

From your laptop to the world

Where could you run your code?

  • Local computer
    • limited resources, not collaborative, messy
  • Institutional services (Onyxia datalab, Jean Zay, CREST server)
    • conditions of access, availability
    • but shared storage, big machines, GPUs
  • Cloud services (Google Colab, Kaggle)
    • proprietary, limited, black box
  • Decidated servers

The comfort zone: your laptop

  • One person, one machine, one folder
  • Everything is visible, clickable, persistent
  • It works… until:
    • the dataset does not fit
    • the script takes a night
    • a teammate needs the same data and the same code
    • your laptop dies the week before the deadline

What changes when you leave your laptop

  • Nothing is persistent by default
  • No mouse, no GUI: command line
  • Resources are requested, shared, and (sometimes) paid
  • Your credentials become the problem
  • Everything has to be written down: scripts, not clicks

This is exactly what makes it reproducible.

The challenge of working together

  • Sharing storage
  • Communicating over various channels
  • Agreeing on tools and conventions
  • Keeping track of various versions

Reproducibility

What is reproducibility

A result or a project is never a one shot.

A result is reproducible when the same analysis steps performed on the same dataset consistently produce the same answer.

…on another machine, by another person, later.

Science loves reproducibility

Different flavours of reproducibility

Why it matters for policy: an example

Reinhart & Rogoff (2010), Growth in a Time of Debt: above 90% of public debt/GDP, growth collapses. Widely cited in austerity debates.

Herndon, Ash & Pollin (2013) asked for the spreadsheet: an Excel formula excluded five countries, plus debatable weighting choices. The threshold effect largely disappears.

Important

It took 3 years and a PhD student to get the file. With open data + a script, it takes an afternoon.

Another example: our Wikipedia analysis

You count the articles mentioning “climate” in French Wikipedia. Six months later, a reviewer asks for the number again.

  • Which dump? (Wikipedia changes every day)
  • Which shards did you download? All of them?
  • Which filter? Case sensitive? “climat” or “climatique”?
  • Which version of your script? Of pandas?
  • On which machine? Did the big shard even fit?

If any answer is “I don’t remember”, the number is not reproducible.

What it entails to be reproducible

Be able to walk the path again: connecting data, software and questions

Openness

Both for data and code, openness creates the possibility of reproducibility

Not always possible for data, especially with sensitive information

What is open science

  • Clear methodologies
  • Data accessibility: FAIR (Findable, Accessible, Interoperable, Reusable)
  • Reusable software (open code, open formats)

How to conciliate privacy with reproducibility

  • As open as possible, as closed as necessary
  • Anonymise / pseudonymise
  • Aggregate
  • Synthetic data

The DevOps connection

DevOps (software development + IT operations) = practices that connect code and its execution

  • version control, automated tests, CI/CD
  • containers, infrastructure as code
  • logs, monitoring

MLOps = the same for data and models: data versioning, pipelines, experiment tracking. LLMOps, you guess…

What research borrows from it

A vocabulary that is invading computational practice

  • Containers (Docker image): a frozen environment
  • Pipelines: a Makefile / run.sh / snakemake with a clear order of steps
  • Logs: know what happened when you were not looking
  • CI: GitHub Actions running tests on each change

Research workflows should be designed with recomputation in mind

The reproducibility ladder

Level What you have
0 a notebook on a laptop
1 script + README + Git
2 + pinned environment + data on shared storage
3 + container / CI
4 + workflow manager on HPC

Target for your project: level 2. Today we set up the storage and the compute; next session the Git part.

How to achieve it: the minimal kit

  1. A Git repository with a README.md: what, how to run, where the data is
  2. A pinned environment: requirements.txt (or pyproject.toml), Python version
  3. Scripts, not only notebooks
  4. Data separated from code: raw data immutable, every transformation scripted
  5. Random seeds, logged parameters, dated outputs

Choosing tools

Tools: who’s who, and what do you use?

Software has consequences

  • Open / proprietary
  • Software / programming
  • Specialised / general purpose

Explainability & maintainability

The idea is to increase stability and the possibility to modify elements

  • Avoid dependencies on paid services and black boxes
  • Use technologies you understand
  • Use technologies used by others (your teammates, your field)

You can resist genAI (yes, it is hard)

Different uses, some more clever than others.

Tip

Good use: “explain this command”, “write the boilerplate”. Bad use: “here is my data, analyse it” (where does the data go? what did it do?).

The role of programming in data science

Important for the flexibility of the workflow

  • Different languages (Python, R, SQL, bash…)
  • Different tools
  • Different workflows

What do you use for programming?

Scripts, notebooks and packages

  • Notebooks allow literate programming
    • very useful for exploration / prototyping
  • Scripts are better for stability, automation, remote execution
  • A pathway: notebook → script → package

Rule of thumb: if it runs more than once, it is a script.

Use adequate tools

(in fact Excel-like tools are fine for specific uses)

Let’s talk about data formats

Format is both information & affordance

Formats: a practical map

Format Pros Cons
CSV universal, human-readable no types, encoding & separators, slow, big
JSON / JSONL nested, streams line by line verbose
Parquet typed, compressed, columnar, splittable binary, needs a library
SQLite / DuckDB relational, joins, SQL one file, one writer

Suggestion: open format + think about how you will access it.

What is a Parquet file (our Wikipedia format)

  • Columnar: read only the columns you need (title without text)
  • Typed schema embedded in the file
  • Compressed (snappy, zstd): 3–10× smaller than CSV
  • Split in row groups: read a slice without loading everything
  • The format of data lakes, Hugging Face, Spark, DuckDB, polars…

On disk ≠ in memory

A 2 GB parquet of text can need 6–10 GB of RAM once loaded in pandas.

What kind of computation do you need?

Resource What it limits
CPU (cores) speed, parallelism
RAM the size of what you can hold: the true bottleneck for data
Disk local = ephemeral & fast; object storage = persistent & shared
GPU deep learning, embeddings, LLMs
Network moving 17 GB is not free

How to think about sizes

Size Example Consequence
1 MB a survey anything works
100 MB a year of admin data, one Simple English shard Excel breaks, pandas is fine
1 GB several years of newspapers, one English shard think about RAM
10–100 GB full English Wikipedia, a month of Reddit stream or sample, remote machine
1 TB+ you need a data engineer

Could you think of examples for each category in your own projects?

Rules of thumb

  • RAM needed ≈ 3–10× the compressed parquet size (text)
  • If it does not fit: stream (row groups, chunks, lazy engines) or sample
  • Favour small data if you can

Otherwise

Solution 1: reduce your data

  • work on a subset / sample
  • read only the columns you need
  • batch

Solution 2: parallelise

  • more cores on one machine (polars, DuckDB, …)
  • more machines (Dask, Spark, HPC jobs)
  • dedicated tools: xan for CSV

Where to run: a decision tree

  • Fits in your laptop RAM, runs in minutes → laptop
  • Needs more RAM / a GPU / hours → Onyxia datalab
  • Needs days, many GPUs, thousands of jobs → HPC (Jean Zay, GENCI)

Start small, then scale.

  1. One file, on a sample → does the code work?
  2. One file, full size → does it fit in memory? how long?
  3. All files, one machine → parallelise
  4. All files, many machines → HPC

Measure at each step: time, peak memory.

Rules before starting

Rule 0: know your data

  • Have a look at your data
    • duplicates, empty data, encoding
  • Before starting complex treatments
    • do simple treatments
    • ask yourself if the question and the data match

Rule 1: structure the project

  • Separate code from data
    • different logic, different tools, different sizes, different rights
  • Document / comment your productions
    • be explicit (variables, README)
    • yes, it is boring, but useful
  • Modularise: create distinct elements
    • one file per step
    • functions rather than repeated code

There will always be another Monday

Rule 2: a common file system

project-name/
│
├── README.md              # what, how to run, where is the data
├── requirements.txt       # pinned environment
├── .gitignore             # data/, .env, outputs
├── data/                  # NOT in git
│   ├── README.md          # -> where the data really is
│   ├── raw/               # original, immutable
│   ├── intermediate/
│   └── processed/         # analysis-ready
├── src/                   # one script per step
├── notebooks/
├── docs/
└── reports/
    ├── figures/
    └── tables/

Rule 2 bis: paths are configuration, not code

Bad

df = pd.read_csv("/Users/emilien/Downloads/final2.csv")

Good

from pathlib import Path
import os
DATA = Path(os.environ.get("DATA_DIR", "data"))
df = pd.read_parquet(DATA / "raw" / "wiki_simple.parquet")

The same script runs on your laptop, on Onyxia, on a teammate’s machine.

Rule 3: accept to spend time on data preparation

In theory / in reality

Avoid correcting your data manually

Build a workflow — write scripts. Raw data is immutable.

Data architecture: aim for tidy data

Take time to transform the data if needed

  • Separate raw data from transformed data
  • Move from unstructured to structured
  • Tidy data: one observation per row, one variable per column

Rule 4: organise for collaboration

  • Comments in the scripts; different files to modularise
  • Git: one branch per person/feature, small commits, review (session 2)
  • Log what you do (print is a start, logging is better)
  • Issues as the shared to-do list
  • Conventions → written in the README

Where to store the data

During the project

  • Laptop: temporary
  • Institutional solutions: S3 on Onyxia
  • Cloud solutions: with care (privacy)

After the project

  • Zenodo, Figshare, Hugging Face datasets, data.gouv.fr

Ideally, a Data Management Plan

Data management plan: a document that lists the data and how you handle it

  • What types of data? What formats?
  • What volume?
  • Where stored during? Where after?
  • Who can access it? Privacy?
  • Naming and versioning strategy?

Tip

For your project: half a page in data/README.md is enough.

Rule 5: never commit secrets

  • S3 keys, Hugging Face tokens, GitHub tokens
  • SSH private keys
  • .env files, config with passwords
  • Personal data

Use .gitignore + environment variables + a .env.example without values.

Tokens, passwords, keys

  • Password: you, everywhere, forever → the worst
  • Token: a service, a scope, an expiry → prefer read-only, short
  • Key pair: a public half you share, a private half you never share

If you leak something: revoke first, then clean the history. Prevention is much cheaper.

Onyxia

What is Onyxia

  • An open-source datalab platform developed by INSEE
  • Instances:
    • GENES: https://onyxia.lab.groupe-genes.fr
    • INSEE SSPCloud: https://datalab.sspcloud.fr
  • Three things behind one interface
    • services launched by the users (Kubernetes)
    • a file browser (S3 object storage)
    • a secret browser (Vault)

User documentation

A common entry for different services

What is a service

  • A container (Docker image: OS + Python + Jupyter / VS Code / RStudio…)
  • running in a pod on a cluster
  • with the resources you asked for (CPU, RAM, GPU, disk)
  • ephemeral: when it stops, its local disk is gone

Important

The pod is compute, not storage.

How to launch one (live)

  1. Catalogue → vscode-python or jupyter-python
  2. Configure: resources, persistence, init script, Git, S3
  3. Launch → wait → open
  4. My services: see, delete, read the logs

Parameters that matter

  • Resources: CPU request / limit, RAM request / limit, GPU
  • Persistence: a volume (survives a restart of the service, not its deletion)
  • Init script: install packages at start
  • Git: a repository cloned at start, your name/email
  • S3: credentials injected as environment variables

Tip

The Kubernetes tab shows the pod events. This is where OOMKilled appears.

What survives what

Where Service restarts Service deleted Datalab down
file on the pod ✗ ✗ ✗
persistent volume ✓ ✗ ✗
S3 bucket ✓ ✓ ✓ (backup)
code on GitHub ✓ ✓ ✓

This is today’s rule, stated as a table.

The command line

Many servers have no window

  • HPC clusters, the CREST server, most cloud machines: no GUI, only a terminal
  • Onyxia gives you a GUI, but the important things (install, download, move data) happen in the terminal
  • Every tool of the ecosystem (git, pip, hf, mc, docker…) is a command

Two philosophies

  • GUI = Graphical User Interface
    • mouse + everything visible
    • “massive” software
  • CLI = Command-Line Interface
    • keyboard (text-based) + everything hidden
    • one small tool per task

small, simple programs with clean interfaces can be combined to build larger systems

What is the command line interface?

A command-line interface (CLI) is a means of interacting with a computer program by inputting lines of text called command-lines

A shell / terminal is a process that serves as a command processor

  • In the past, every computer
  • Now, mainly Unix systems (Linux, macOS…) and programming
  • Different shells (bash, zsh…) with a common philosophy

Why do I have to care about CLI?

  • Formalise all treatments to allow reproducibility (a command can be copied; a click cannot)
  • Use different types of remote computers (datalab, HPC)
  • Mix it with scripts (Python, R)
  • Use specific tools (git, hf, mc, xan…)
  • Combine existing tools into powerful pipelines

*nux systems in research

Linux (and Unix)

  • largely used in research
  • infrastructure of computing resources (Linux runs all the TOP500 supercomputers)
  • pervasive in a lot of tools

Beyond

  • Free and open (nobody owns it)
  • Diversity of versions: Debian (Ubuntu), Red Hat, SUSE…
  • On Windows: Windows Subsystem for Linux

This is overly complicated!

You don’t have to master all of it

  • You will use only specific commands
  • You can search / ask an LLM
  • And you can make different attempts: it is a dialogue

First, the structure of a command

  • a name for a tool (for instance find)
  • options with a flag (-o VALUE / --option VALUE)
  • arguments (potentially multiple)

Help is always in the same place

man command or command --help

Second: files, directories, processes

  • A file = a collection of data on non-volatile storage. It has a location in the file system called a path.
  • A directory is a special file holding information about other files: a container for files or directories.
  • A process is an executing program that needs volatile storage (RAM) and CPU.

Third: the file system

  • Organised from a root: / (Unix) or C:\ (Windows)
  • The file system is a tree 🌲
    • Absolute path: from the root. Depends on the computer.
    • Relative path: from the current location. Each program is running from somewhere: .

First commands

  • pwd: the current working directory
  • ls: list the files in a folder (-l long, -h human sizes, -a hidden)
  • cd: change directory
  • mkdir: create a folder (-p for nested)
  • touch: create an empty file
  • cp: copy a file
  • mv: move / rename a file
  • rm: remove a file (-r for a directory; no trash bin)

Let’s have a quick look in the Onyxia terminal

Tips

  • Up/Down arrows: previous commands
  • Tab: completion
  • ..: parent folder
  • ~: home
  • history 20: the last 20 commands
  • Wildcard matching: *
  • Ctrl+C: stop what is running

More useful commands

  • echo: print text
  • cat: display a file
  • head / tail: the beginning / end of a file (-n 5)
  • wc: count lines, words, bytes (-l)
  • find: find files
  • grep: search text (global / regular expression / print)
  • sort, uniq: sort, deduplicate
  • du -sh *: disk usage of each file
  • df -h: free disk space

More (just to know they exist)

  • top / htop: see running processes
  • ps: list processes; kill: stop one
  • nano / vim: edit text files in the terminal
  • curl / wget: download files
  • unzip, tar, gzip: (de)compress
  • chmod: change permissions
  • sudo: run as administrator

Successive commands: the pipe

  • Redirect output to a file: > (write) and >> (append)
  • Pipe the output of one command into the next: |
ls -l | wc -l                     # how many files
find . -name "*.parquet" | wc -l  # how many parquet files
du -sh data/raw/* | sort -h       # files by size

Variables and environment variables

  • echo $HOME, echo $PATH
  • env: all the environment variables of the shell
  • export VAR=value: set a variable, visible by the programs you launch
  • which python: where is this command?

On Onyxia

Your S3 credentials are environment variables: env | grep AWS

File permissions

Permissions are what a user can do with a file

  • ls -l: mode shown as read-write-execute (rwx) for user, group, others
  • chmod u+x script.sh: make a file executable
  • chmod 600 key: readable only by you (what SSH wants for a private key)

Install a tool

  • Each OS has a package manager: apt-get (Debian), brew (macOS), choco (Windows)
  • Python tools come with pip
sudo apt-get update && sudo apt-get install -y tree
pip install huggingface_hub

Note

On Onyxia, installations disappear with the service. Put them in the init script or in requirements.txt.

S3 from Python

import os
import pandas as pd

storage_options = {
    "client_kwargs": {"endpoint_url": os.environ["AWS_S3_ENDPOINT"]},
    "key": os.environ["AWS_ACCESS_KEY_ID"],
    "secret": os.environ["AWS_SECRET_ACCESS_KEY"],
    "token": os.environ["AWS_SESSION_TOKEN"],
}
df = pd.read_parquet("s3://my-bucket/wiki/wiki_simple_01.parquet",
                     columns=["id", "title"],
                     storage_options=storage_options)
